Planning exists because “break the work into tasks” is unsafe if the planner does not first understand the system those tasks will change.

<div className="callout good"><strong>Choose the simplest useful pattern. Heavier process is not more mature.</strong> Increase planning depth, review, model capability, and orchestration only when task shape or evidence warrants it.</div>

<div className="grid four">
  <div className="card"><h3>What it is</h3><p className="muted">Architecture-aware solution design: orient to the Contract, current architecture/codebase, and existing Architecture Decision Records (ADRs) <InfoTip label="Architecture Decision Record">A durable record of an architecturally significant decision: context, options, rationale, and consequences.</InfoTip>; then choose architecture, verification, decomposition, tasks, dependencies, and execution pattern.</p></div>
  <div className="card"><h3>Why it matters</h3><p className="muted">A coding agent can solve one ticket beautifully while damaging the whole system.</p></div>
  <div className="card"><h3>Failure prevented</h3><p className="muted">Architecture-blind decomposition and hidden coupling.</p></div>
  <div className="card purple-line"><h3>Core philosophy</h3><p className="muted">Tasks are the output of system understanding—not a substitute for it.</p></div>
</div>
